# Namespaces in C#

## Was sind Namespaces in C#?

Ein ``Namespace`` in C# ist eine **logische Gruppierung** von ``Klassen``, ``Strukturen``, ``Schnittstellen`` und anderen ``Typen``. Sie werden verwendet, um **Namenskonflikte** zu vermeiden und den Code besser zu organisieren. 

In C# sind ``Namespaces`` so etwas wie **Container** für ``Typen``, die es einfacher machen, ähnliche ``Typen`` zusammenzufassen und den Code übersichtlicher zu halten. Ein ``Namespace`` ist eine **abstrakte Bezeichnung** und keine zwingende **physische Dateistruktur** (wie bestimmte Ordnerhierarchien). Der Name des ``Namespaces`` korreliert in der Praxis jedoch oft mit der Ordnerstruktur des Projekts, um die Organisation und Übersichtlichkeit zu erleichtern.

## Verwendung von Namespaces in C#

### Kurzform der Verwendung von Namespaces (using):
In C# ist die Verwendung eines ``Namespaces`` in der Regel mit dem ``Schlüsselwort`` `using` verbunden. Dieses wird verwendet, um einen ``Namespace`` zu importieren, sodass Sie auf die darin enthaltenen ``Typen`` zugreifen können, ohne den vollständigen ``Namespace``-Namen zu schreiben.

Beispiel für die Verwendung eines ``Namespaces`` in C#:
```csharp
using System;

namespace MyApplication
{
    class Program
    {
        static void Main(string[] args)
        {
            Console.WriteLine("Hello, World!");
        }
    }
}
```

- `using System;` importiert den `System`-``Namespace``, damit Sie die ``Klasse`` `Console` verwenden können, ohne den vollständigen Namen `System.Console` schreiben zu müssen.

### Längere Schreibweise ohne using:
Wenn Sie den `using`-Befehl nicht verwenden, müssen Sie den vollständigen ``Namespace``-Pfad angeben, wenn Sie auf einen ``Typ`` zugreifen.

Beispiel ohne `using`:
```csharp
namespace MyApplication
{
    class Program
    {
        static void Main(string[] args)
        {
            System.Console.WriteLine("Hello, World!");
        }
    }
}
```

In diesem Fall müssen Sie den gesamten ``Namespace`` `System.Console` schreiben, um auf die ``Klasse`` `Console` zuzugreifen.

## Top-Level Statements und Namespaces (seit C# 9)

Mit C# 9 wurden sogenannte ``Top-Level Statements`` eingeführt. Sie erlauben es, den Code für den Einstiegspunkt der Anwendung direkt auf Dateiebene zu schreiben, ohne explizit eine ``Klasse`` `Program` und eine ``Methode`` `Main` deklarieren zu müssen. Dies macht den Code kürzer und lesbarer.

### Besonderheit bezüglich Namespaces:
Code, der als ``Top-Level Statement`` geschrieben wird, befindet sich **immer** im **globalen Namespace**. Der ``Compiler`` generiert im Hintergrund automatisch die ``Klasse`` `Program` mit der ``Methode`` `Main`.

Beispiel für ein ``Top-Level Statement`` (z. B. in einer `Program.cs`):
```csharp
using System;

// Kein Namespace, keine class, kein Main() nötig
Console.WriteLine("Hello, World!");
```

### Konflikte mit Namespaces vermeiden
Da ``Top-Level Statements`` im **globalen Namespace** leben, kann es zu ``Compiler``-Fehlern kommen, wenn man sie falsch mit **dateibezogenen** ``Namespaces`` (`namespace MeinNamespace;`) kombiniert. 

Ein **dateibezogener** ``Namespace`` gilt für die *gesamte* Datei. Da ``Top-Level Statements`` aber global sein müssen, verbietet C# diese Kombination in derselben Datei:

**Falsch (Führt zu einem Fehler):**
```csharp
namespace MeinProjekt;

Console.WriteLine("Das funktioniert nicht!"); // Fehler, da Namespace und Top-Level kollidieren
```

**Best Practice:** Normalerweise belässt man die ``Top-Level Statements`` allein in der `Program.cs` und legt andere ``Klassen`` (mit ihren jeweiligen ``Namespaces``) sauber getrennt in separaten Dateien ab.

### Namenskonflikte zwischen Klassen und Namespaces
Ein häufiger Fehler bei der Nutzung von ``Top-Level Statements`` ist es, einen ``Namespace`` und eine ``Klasse`` exakt gleich zu benennen. 

**Falsch:**
```csharp
using Hamster;

// Der Compiler denkt, das erste "Hamster" ist der Namespace.
Hamster meinHamster = new Hamster(); 
```
*Lösung:* Benenne den ``Namespace`` immer anders als die ``Klasse`` (z. B. ``Namespace`` `Tiere` oder `HamsterProjekt`, ``Klasse`` `Hamster`), um Probleme bei der ``Instanziierung`` zu verhindern.

## Zusammenfassung:
- ``Namespaces`` sind **logische Gruppierungen** von ``Klassen`` und anderen ``Typen``, die hauptsächlich dazu dienen, **Namenskonflikte** zu vermeiden und den Code zu organisieren.
- Man importiert ``Namespaces`` mit dem ``Schlüsselwort`` `using` und hat die Wahl zwischen der kurzen (mit `using`) oder der langen (vollqualifizierten) Schreibweise.
- ``Top-Level Statements`` laufen stets im **globalen Namespace**. Sie dürfen in derselben Datei nicht mit **dateiweiten** ``Namespaces`` (`namespace X;`) gemischt werden. **Block-Namespaces** (`namespace X { ... }`) sind unterhalb der ``Top-Level Statements`` jedoch erlaubt.
- Vermeide es grundsätzlich, einem ``Namespace`` denselben Namen wie einer ``Klasse`` zu geben, um **Namenskonflikte** bei der ``Instanziierung`` zu verhindern.
