#### Wir merken uns von [Git als Linked List & Zeitspeicher](L02.0Git-part-1.html):

| Befehl | Was passiert | Wo liegt die Änderung danach? |
|---|---|---|
| ``git clone <adresse>`` | holt das [``Remote Repository``](../../../05_Glossar.md#remote-repository) auf den Rechner | lokales [``Repository``](../../../05_Glossar.md#repository) |
| ``git status`` | zeigt, was geändert (rot) und was gestaged (grün) ist | – |
| ``git add Datei.cs`` / ``git add -A`` | legt eine / alle Dateien auf den Packtisch | [``Staging Area``](../../../05_Glossar.md#staging-area) |
| ``git commit -m "Add ..."`` | macht aus dem Packtisch einen neuen Knoten | lokales [``Repository``](../../../05_Glossar.md#repository) |
| ``git log --oneline`` | zeigt die [``Commits``](../../../05_Glossar.md#commit), neuester zuerst | – |
| ``git push`` | überträgt fehlende [``Commits``](../../../05_Glossar.md#commit) zum Server | [``Remote Repository``](../../../05_Glossar.md#remote-repository) |
| ``git reset Datei.cs`` | nimmt die Datei vom Packtisch, Änderung **bleibt** | [``Working Directory``](../../../05_Glossar.md#working-directory) |
| ``git checkout -- Datei.cs`` | setzt die Datei auf den letzten [``Commit``](../../../05_Glossar.md#commit) zurück, Änderung ist **weg** | nirgends ⚠️ |

>1. [``Git``](../../../05_Glossar.md#git) speichert die Geschichte unseres Projekts als Kette von [``Commits``](../../../05_Glossar.md#commit). Jeder [``Commit``](../../../05_Glossar.md#commit) ist ein Knoten, der die Änderungen (*Diff*) und eine [``Referenz``](../../../05_Glossar.md#referenz) auf seinen Vorgänger (*Parent*) speichert – wie eine *Linked List*.
>2. [``HEAD``](../../../05_Glossar.md#head) ist ein Zeiger auf den [``Commit``](../../../05_Glossar.md#commit), auf dem wir gerade arbeiten. Nach jedem neuen [``Commit``](../../../05_Glossar.md#commit) wandert [``HEAD``](../../../05_Glossar.md#head) auf diesen neuen Knoten weiter.
>3. Bevor wir Befehle ausführen, wechseln wir im Terminal mit ``cd`` in den Projektordner. Dort liegt im versteckten Ordner ``.git`` unser lokales [``Repository``](../../../05_Glossar.md#repository).
>4. Eine Datei durchläuft drei Bereiche: das [``Working Directory``](../../../05_Glossar.md#working-directory) (unsere Dateien auf der Festplatte), die [``Staging Area``](../../../05_Glossar.md#staging-area) (der *Packtisch* für den nächsten [``Commit``](../../../05_Glossar.md#commit)) und das [``Repository``](../../../05_Glossar.md#repository) (die gespeicherten [``Commits``](../../../05_Glossar.md#commit)).
>5. ``git status`` zeigt uns, in welchem Bereich welche Datei liegt: *rot* bedeutet geändert, aber nicht gestaged, *grün* bedeutet gestaged.
>6. ``git add Datei.cs`` legt gezielt **eine** Datei auf den Packtisch. ``git add -A`` legt **alle** geänderten, neuen und gelöschten Dateien auf einmal darauf.
>7. ``git commit -m "..."`` erzeugt aus dem Inhalt der [``Staging Area``](../../../05_Glossar.md#staging-area) einen neuen Knoten. Die Nachricht ist ein kurzer Satz, der mit einem Verb im Imperativ beginnt und sagt, *was* der [``Commit``](../../../05_Glossar.md#commit) tut, z. B. ``"Add custom exceptions"``.
>8. ``git log --oneline`` zeigt die Kette der [``Commits``](../../../05_Glossar.md#commit) vom neuesten zum ältesten.
>9. Neue [``Commits``](../../../05_Glossar.md#commit) existieren zuerst nur **lokal**. Das [``Remote Repository``](../../../05_Glossar.md#remote-repository) am Server heißt ``origin``, dessen Stand zeigt der Zeiger ``origin/main``.
>10. ``git push`` vergleicht die lokale Kette mit der am Server, überträgt die fehlenden Knoten und zieht ``origin/main`` nach.
>11. ``git reset Datei.cs`` nimmt eine Datei von der [``Staging Area``](../../../05_Glossar.md#staging-area) zurück ins [``Working Directory``](../../../05_Glossar.md#working-directory) (*Unstage*). Die Änderung in der Datei bleibt **erhalten**.
>12. ``git checkout -- Datei.cs`` überschreibt die Datei im [``Working Directory``](../../../05_Glossar.md#working-directory) mit dem Stand des letzten [``Commits``](../../../05_Glossar.md#commit). Die ungespeicherte Änderung ist danach **unwiderruflich** weg, denn sie war nie in einem [``Commit``](../../../05_Glossar.md#commit).
>13. Erst ``git reset``, dann ``git checkout``: So entfernen wir eine versehentlich gestagte, kaputte Änderung vollständig.

#### Wir merken uns von der [Zettelübung Git & Bubble Sort](../ZettelUebungen/01_BubbleSort/git_bubble_sort.md):
>1. Ein neues Projekt legen wir zuerst am GitLab-Server der Schule an. Danach holen wir es mit ``git clone <adresse>`` als lokales [``Repository``](../../../05_Glossar.md#repository) auf den Rechner.
>2. Unter *Manage → Members* fügen wir die Lehrperson mit der Rolle **Reporter** hinzu. Diese Rolle darf nur lesen.
>3. ``dotnet new console`` erstellt das Projekt, ``dotnet new gitignore`` die [``.gitignore``](../../../05_Glossar.md#gitignore). Darin steht, was **nicht** ins [``Repository``](../../../05_Glossar.md#repository) gehört: die Ordner ``bin`` und ``obj``, denn der [``Compiler``](../../../05_Glossar.md#compiler) erzeugt sie jederzeit neu.
>4. Ein [``Commit``](../../../05_Glossar.md#commit) enthält **eine** sinnvolle Änderung, die sich übersetzen lässt. So entsteht eine Kette, die aufeinander aufbaut.
>5. Nach ``git push`` kontrollieren wir **im Browser** am Server, ob alle [``Commits``](../../../05_Glossar.md#commit) angekommen sind.
>6. Kaputter Code kommt nie in einen [``Commit``](../../../05_Glossar.md#commit). Wir nehmen ihn mit ``git reset`` und ``git checkout --`` zurück, bevor wir committen.
>7. Bubble Sort vergleicht benachbarte [``Elemente``](../../../05_Glossar.md#element) und vertauscht sie, wenn sie falsch herum stehen. Nach jedem Durchlauf steht das größte unsortierte Element ganz rechts. Gab es in einem Durchlauf keine Vertauschung mehr, ist das [``Array``](../../../05_Glossar.md#array) sortiert, und wir brechen ab.
>8. Ist das [``Array``](../../../05_Glossar.md#array) ``null``, werfen wir eine ``ArgumentNullException``: Ohne Daten kann die [``Methode``](../../../05_Glossar.md#methode) nicht sortieren.

#### Wir merken uns von [Exceptions vs. Kontrollstrukturen](L02.1Exceptions.html):
>1. Eine [``Exception``](../../../05_Glossar.md#exception) ist ein [``Objekt``](../../../05_Glossar.md#objekt), das einen **echten Ausnahmefall** beschreibt. Wir verwenden sie, wenn eine [``Methode``](../../../05_Glossar.md#methode) ihre Aufgabe nicht erfüllen und das Problem **nicht selbst lösen** kann.
>2. Mit dem [``Schlüsselwort``](../../../05_Glossar.md#schlüsselwort) ``throw`` werfen wir eine [``Exception``](../../../05_Glossar.md#exception), z. B. ``throw new InvalidOperationException("...")``. Die [``Methode``](../../../05_Glossar.md#methode) bricht sofort ab, und die [``Exception``](../../../05_Glossar.md#exception) wandert zur aufrufenden [``Methode``](../../../05_Glossar.md#methode) zurück.
>3. Der ``try``-Block umschließt Code, in dem eine [``Exception``](../../../05_Glossar.md#exception) auftreten kann ([``try-catch-finally``](../../../05_Glossar.md#try-catch-finally)). Tritt eine auf, werden alle weiteren Zeilen im ``try``-Block **übersprungen**.
>4. Der ``catch``-Block fängt eine passende [``Exception``](../../../05_Glossar.md#exception) auf. In der Variable ``ex`` stecken alle Informationen über den Fehler, z. B. ``ex.Message``. Der ``catch``-Block wird nur betreten, wenn im ``try``-Block tatsächlich ein passender Fehler geworfen wurde.
>5. Der ``finally``-Block wird **immer** ausgeführt: egal ob alles gut ging, ein Fehler behandelt wurde oder ein ``return`` im ``try`` oder ``catch`` stand. Wir verwenden ihn, um Ressourcen wie Dateien, Verbindungen oder Ports sicher wieder freizugeben.
>6. Wir werfen immer die **passendste** [``Exception``](../../../05_Glossar.md#exception): ``ArgumentNullException`` (ein Argument ist ``null``), ``ArgumentOutOfRangeException`` (ein Wert liegt außerhalb des gültigen Bereichs), ``ArgumentException`` (ein Argument ist falsch), ``InvalidOperationException`` (das [``Objekt``](../../../05_Glossar.md#objekt) ist im falschen [``Zustand``](../../../05_Glossar.md#zustand)) oder ``FileNotFoundException`` (eine Datei fehlt).
>7. C# prüft die ``catch``-Blöcke von oben nach unten, und der **erste passende** gewinnt. Deshalb sortieren wir von der speziellsten [``Klasse``](../../../05_Glossar.md#klasse) (oben) zur allgemeinsten [``Basisklasse``](../../../05_Glossar.md#basisklasse) (unten). Ein Beispiel: ``ArgumentOutOfRangeException`` steht vor ``ArgumentException``, und diese steht vor ``Exception``.
>8. Mit ``when`` fangen wir eine [``Exception``](../../../05_Glossar.md#exception) nur dann, wenn zusätzlich eine Bedingung erfüllt ist ([``Exception Filter``](../../../05_Glossar.md#exception-filter)), z. B. ``catch (ZutatLeerException ex) when (ex.Zutat == "Milch")``. Liefert ``when`` den Wert ``false``, wird der nächste passende ``catch``-Block geprüft.
>9. ``catch (Exception ex)`` darf höchstens als **letztes** Fangnetz stehen. Steht er weiter oben, kann kein ``catch``-Block darunter je erreicht werden, und der Compiler meldet den Fehler ``CS0160``.
>10. Wollen wir einen Fehler nach dem Protokollieren weiterreichen, schreiben wir ``throw;``. Mit ``throw ex;`` geht der ursprüngliche [``StackTrace``](../../../05_Glossar.md#stacktrace) verloren, also die Stelle, an der der Fehler wirklich passiert ist.
>11. Anti-Patterns vermeiden wir:
>       1. ``throw new Exception(...)``: Der Aufrufer kann die Fehler nicht mehr unterscheiden.
>       2. ``catch (Exception) { }`` („Pokémon-Catch“): Damit werden echte Programmierfehler versteckt.
>       3. ``throw ex;``: Der [``StackTrace``](../../../05_Glossar.md#stacktrace) geht verloren.
>12. Eine eigene [``Exception``](../../../05_Glossar.md#exception) ist eine [``abgeleitete Klasse``](../../../05_Glossar.md#abgeleitete-klasse) von ``Exception`` (``: Exception``). Ihr Name endet auf ``...Exception``. Den Fehlertext reichen wir im [``Konstruktor``](../../../05_Glossar.md#konstruktor) mit ``: base(nachricht)`` an die [``Basisklasse``](../../../05_Glossar.md#basisklasse) weiter.
>13. Eine eigene [``Exception``](../../../05_Glossar.md#exception) kann zusätzliche [``Eigenschaften``](../../../05_Glossar.md#eigenschaft) haben, z. B. ``Zutat``, ``Benoetigt`` und ``Vorhanden``. So bekommt der Aufrufer im ``catch`` genaue Werte und kann **gezielt** reagieren, z. B. mit ``when (ex.Zutat == "Milch")``.
>14. ``ex.Message`` liefert nur den kurzen Fehlertext für Benutzer:innen. ``ex.StackTrace`` zeigt die Aufrufkette mit Methodennamen und Zeilennummern. ``ex.ToString()`` kombiniert Typ, Nachricht und [``StackTrace``](../../../05_Glossar.md#stacktrace) und ist das Standardformat für Logdateien.
>15. Fehlermeldungen heben wir mit ``Console.ForegroundColor = ConsoleColor.Red;`` hervor. Danach rufen wir **immer** ``Console.ResetColor();`` auf.
>16. Ein **erwartbarer Fall** wird mit einer [``Kontrollstruktur``](../../../05_Glossar.md#kontrollstruktur) (``if``, ``while``, ``bool``) oder einem [``Rückgabewert``](../../../05_Glossar.md#rückgabewert) gelöst, **nicht** mit einer [``Exception``](../../../05_Glossar.md#exception). Beispiele sind ein Tippfehler bei einer Eingabe, ein Stein am Spielfeld oder der Rand des Spielfelds.
>17. Gibt es eine ``Try...``-[``Methode``](../../../05_Glossar.md#methode) (``int.TryParse``, ``double.TryParse``), verwenden wir sie statt ``Parse`` im ``try-catch``. Sie liefert ``true`` oder ``false`` und schreibt das Ergebnis über einen [``Ausgangsparameter``](../../../05_Glossar.md#ausgangsparameter) (``out``) in eine Variable. Eine [``Exception``](../../../05_Glossar.md#exception) zu werfen dauert ein Vielfaches länger als eine ``if``-Abfrage.
>18. Einen **echten Ausnahmefall** (z. B. einen Achsbruch) behandeln wir im ``catch`` auf eine von zwei Arten:
>       1. **Nicht behebbar:** Wir protokollieren mit ``File.AppendAllText(datei, text)`` (Zeitpunkt mit ``DateTime.Now`` und ``ex.ToString()``) und stoppen kontrolliert.
>       2. **Behebbar:** Wir protokollieren und reparieren den [``Zustand``](../../../05_Glossar.md#zustand) (*Kompensation*), z. B. indem wir das defekte [``Objekt``](../../../05_Glossar.md#objekt) durch ein neues ersetzen.

#### Wir merken uns von [Aufgabe01 – Kaffeeautomat Pro](../Aufgabe01-Kaffeeautomat/Angabe.md):
>1. Die Frage ist immer: Ist der Fall **erwartbar**, und kann die [``Methode``](../../../05_Glossar.md#methode) ihre Aufgabe **trotzdem** erfüllen? Dann lösen wir ihn mit einem [``Guard``](../../../05_Glossar.md#guard-clause) (Zeile überspringen, Warnung ausgeben). Sonst werfen wir eine [``Exception``](../../../05_Glossar.md#exception).
>2. In einer von Hand getippten [``CSV-Datei``](../../../05_Glossar.md#csv) sind Leerzeilen, Kommentare, falsche Spaltenanzahl oder leere Namen **erwartbar**. Sie werden mit einem [``Guard``](../../../05_Glossar.md#guard-clause) übersprungen. Fehlt die Datei ganz, ist das eine ``FileNotFoundException``.
>3. Jede [``Methode``](../../../05_Glossar.md#methode) prüft nur, wofür sie **zuständig** ist. Ob ein Getränk auf der Karte steht, entscheidet der Kaffeeautomat (``SucheGetraenk``), nicht das Einlesen der Datei.
>4. Ein Setter mit [``field``](../../../05_Glossar.md#field-keyword) wirft bei einem ungültigen Wert eine ``ArgumentOutOfRangeException``. So kann das [``Objekt``](../../../05_Glossar.md#objekt) **nie** in einen ungültigen [``Zustand``](../../../05_Glossar.md#zustand) kommen.
>5. Ein Überlauf beim Auffüllen ist erwartbar: Wir melden ihn über den [``Rückgabewert``](../../../05_Glossar.md#rückgabewert) (übergelaufene Menge). Eine Menge von ``0`` oder weniger ist dagegen ein falscher [``Aufruf``](../../../05_Glossar.md#aufruf) und damit eine [``Exception``](../../../05_Glossar.md#exception).
>6. **Erst alles prüfen, dann ändern:** ``Bruehe`` prüft mit ``PruefeMenge`` zuerst **alle** Behälter ([``Delegieren``](../../../05_Glossar.md#delegieren)) und entnimmt erst danach. Sonst wären Wasser und Bohnen schon weg, wenn die Milch fehlt.
>7. Der **Aufrufer** entscheidet im ``catch``, ob er das Problem beheben kann (einschalten, entkalken, nachfüllen) und es **nochmal versucht**, oder ob er die Bestellung **überspringt**.
>8. Einen erneuten Versuch bauen wir mit einer ``while``-Schleife und einer ``bool``-Variable ``erledigt``. Damit keine Endlosschleife entsteht, wird nach ``MaxVersuche`` Fehlschlägen übersprungen.
>9. Im ``finally`` geben wir nach **jedem** Versuch den ``Status()`` aus, egal ob er geklappt hat oder nicht.
>10. Mit ``this`` übergibt der Automat sich selbst an seine Behälter. So kennt jeder Behälter genau seinen Automaten ([``Bidirektionalität``](../../../05_Glossar.md#bidirektionalität) auf [``Objektebene``](../../../05_Glossar.md#objektebene)).
>11. Eine Benutzereingabe ist **erwartbar** falsch: Wir lesen sie mit ``int.TryParse`` in einer Schleife, bis eine Zahl kommt. Ob die Zahl sinnvoll ist, prüft die [``Methode``](../../../05_Glossar.md#methode), die sie verwendet (``Auffuellen``).
>12. Nach jeder Teilaufgabe gibt es einen [``Commit``](../../../05_Glossar.md#commit), der sich übersetzen lässt. Absichtlich eingebaute Fehler werfen wir mit ``git checkout --`` (ungestaged) bzw. ``git reset`` + ``git checkout --`` (gestaged) wieder weg. Sie tauchen in keinem [``Commit``](../../../05_Glossar.md#commit) auf.

#### Wir merken uns von [Generics](L02.2Generics.html):
>1. Mit [``Generics``](../../../05_Glossar.md#generics) schreiben wir eine [``Klasse``](../../../05_Glossar.md#klasse) oder [``Methode``](../../../05_Glossar.md#methode) **nur einmal** für beliebige [``Typen``](../../../05_Glossar.md#typ). Der [``Typparameter``](../../../05_Glossar.md#typparameter) ``T`` ist ein Platzhalter, der erst bei der Verwendung festgelegt wird, z. B. ``DoublyLinkedList<int>`` oder ``DoublyLinkedList<string>``.
>2. Eine generische [``Collection``](../../../05_Glossar.md#collection) wie ``DoublyLinkedList<T>`` speichert Knoten mit ``Data`` vom [``Typ``](../../../05_Glossar.md#typ) ``T`` und den [``Referenzen``](../../../05_Glossar.md#referenz) ``Prev`` und ``Next``.
>3. Bei [``Werttypen``](../../../05_Glossar.md#werttyp) wie ``int`` verhindern [``Generics``](../../../05_Glossar.md#generics) teures [``Boxing``](../../../05_Glossar.md#boxing)/Unboxing (das Ein- und Auspacken in ein ``object``).
>4. Ohne Einschränkung weiß der Compiler über ``T`` nur, was ``System.Object`` kann. Mit einer [``Typ-Restriktion``](../../../05_Glossar.md#typ-restriktion) (``where``) legen wir fest, welche [``Typen``](../../../05_Glossar.md#typ) für ``T`` erlaubt sind. Ein Beispiel: Nach ``where T : Waggon`` können wir in der [``Klasse``](../../../05_Glossar.md#klasse) sicher auf alle [``Eigenschaften``](../../../05_Glossar.md#eigenschaft) von ``Waggon`` zugreifen.
>5. [``Typ-Restriktionen``](../../../05_Glossar.md#typ-restriktion) lassen sich kombinieren:
>       1. ``where T : class`` erlaubt nur [``Referenztypen``](../../../05_Glossar.md#referenztyp).
>       2. ``where T : struct`` erlaubt nur [``Werttypen``](../../../05_Glossar.md#werttyp).
>       3. ``where T : IComparable<T>`` verlangt, dass ``T`` das [``Interface``](../../../05_Glossar.md#interface) implementiert.
>       4. ``where T : new()`` verlangt einen parameterlosen [``Konstruktor``](../../../05_Glossar.md#konstruktor).
>6. Auch in einer nicht generischen [``Klasse``](../../../05_Glossar.md#klasse) kann eine einzelne [``Methode``](../../../05_Glossar.md#methode) einen eigenen [``Typparameter``](../../../05_Glossar.md#typparameter) haben, z. B. ``void Swap<T>(ref T a, ref T b)``.
>7. Werte vom [``Typ``](../../../05_Glossar.md#typ) ``T`` können nicht direkt mit ``<`` oder ``>`` verglichen werden. Mit ``where T : IComparable<T>`` steht uns ``.CompareTo()`` zur Verfügung.
>8. Beim Aufruf leitet der Compiler ``T`` meist selbst aus den Argumenten ab (*Typinferenz*): ``Swap(ref a, ref b)`` statt ``Swap<int>(ref a, ref b)``.
>9. Auch wenn ``GueterWaggon`` von ``Waggon`` erbt, darf eine ``DoublyLinkedList<GueterWaggon>`` **nicht** einer Variable vom [``Typ``](../../../05_Glossar.md#typ) ``DoublyLinkedList<Waggon>`` zugewiesen werden. Sonst könnte man über die allgemeine [``Referenz``](../../../05_Glossar.md#referenz) einen falschen Waggon einfügen.
>10. *Bonus:* Gibt ein [``Interface``](../../../05_Glossar.md#interface) ``T`` **nur zurück** (z. B. ``IEnumerable<out T>``), ist die Zuweisung von speziell zu allgemein erlaubt (*Kovarianz*, ``out``). Nimmt es ``T`` **nur entgegen** (z. B. ``IComparer<in T>``), ist es umgekehrt (*Kontravarianz*, ``in``).
